Work on multiple branches at once with git worktree (no stashing)

You're deep in a feature, and a hotfix lands. The usual dance is git stash, switch, fix, switch back, git stash pop, and hope nothing conflicts. A worktree skips all of it: the other branch simply lives in another folder.

What a worktree is

A repository has one .git directory (history, branches, config) and, normally, one working folder. git worktree add creates additional working folders that all share that same .git. Each has its own checked-out branch, its own index and its own uncommitted changes. Commits made in one are immediately visible in the others, because there is only one object database.

The commands you need

# new branch in a sibling folder, based on main
git worktree add -b hotfix/login ../myapp-hotfix main

# an existing branch
git worktree add ../myapp-review feature/search

# a remote branch you want to review (creates a local tracking branch)
git fetch origin
git worktree add ../myapp-pr-482 -b pr-482 origin/feature/payments

# see them all
git worktree list

# done: remove the folder and its record
git worktree remove ../myapp-hotfix

Put worktrees next to your repo, not inside it, or your editor and file watchers will index them twice. A naming pattern like <repo>-<purpose> keeps ls .. readable.

The one rule that bites: a branch can be checked out once

Try to check out a branch that another worktree already has and git stops you:

fatal: 'feature/search' is already used by worktree at '/code/myapp-review'

That's deliberate: two working copies moving one branch pointer would overwrite each other's commits. Your options: go to the worktree that has it, make a new branch from it, or use git worktree add --detach <path> <commit> when you only want to look or build. The same lock applies to the main checkout, so a branch checked out in your original folder can't be added elsewhere either.

A workflow that actually works

  1. Keep the main folder on a stable branch (often main) and treat it as your "home" for pulling and cloning fresh state.
  2. One worktree per task, created when you start it, removed when it merges. Short-lived worktrees don't pile up.
  3. Hotfix: git worktree add -b hotfix/x ../app-hotfix origin/main, fix, push, open the PR, remove the folder. Your feature work never moved.
  4. Reviewing a PR: add a worktree for its branch, run the tests there, and leave your own work untouched. This beats stash-and-switch because your dev server and build caches in the other folder keep running.

What doesn't come along

  • Ignored files. node_modules, .env, build output and local config exist only where they were created. Each new worktree needs its own install and copies of local config. See the gotchas guide for tactics.
  • Disk. Source files are duplicated per worktree (history is not). For big monorepos with heavy dependencies this adds up: remove worktrees you finished with.
  • Submodules. Support in linked worktrees has historically been rough. Test your repo before relying on it.

Cleaning up

git worktree remove ../app-hotfix        # refuses if there are uncommitted changes
git worktree remove --force ../app-hotfix # discards them
git worktree prune                        # drop records for folders you deleted by hand
git branch -d hotfix/x                    # the branch itself is separate

Removing a worktree doesn't delete its branch, and deleting a branch doesn't remove its worktree. Do both.

FAQ

Why can't I check out the same branch in two worktrees?

Git refuses because two working copies moving the same branch pointer would silently overwrite each other's commits. Create a new branch from it, or use --detach for a read-only look.

Do worktrees share the same git history?

Yes. One object database, refs and config are shared, so a commit in one worktree is instantly visible in the others. Only working files, index and HEAD are separate.

How do I delete a worktree?

git worktree remove <path>. If you deleted the folder manually, run git worktree prune.
